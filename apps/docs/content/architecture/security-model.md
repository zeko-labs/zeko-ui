Zeko's security model is deeply intertwined with that of the Mina Protocol, upon which it is built as a Layer 2 ZK Rollup. By leveraging Mina's infrastructure and zero-knowledge proof system, Zeko aims to inherit key security properties and provide enhanced capabilities.

## How Zeko Inherits and Provides Security

Zeko functions as a ZK Rollup operating on top of the Mina Protocol. Its design specifically aims to leverage the security and tooling that Mina offers.

- **Leveraging Mina's ZK Proof System:** At its core, Mina Protocol is powered by a multi-tiered recursive zkSNARK system, implemented through Kimchi and Pickles. This system supports arbitrary infinite recursive proof construction and notably requires no trusted setup. Zeko reuses most of Mina's transaction snark infrastructure.
- **Transaction Proofs and Batching:** Zeko utilises zk-SNARKs to prove the validity of transactions and compress the computation required to verify them. A transaction snark proves the transition from one ledger state to another. Zeko composes these proofs into a binary tree, where the root snark serves as a proof for a batch of L2 transactions.
- **Commitment to Layer 1:** The sequencer, which processes L2 transactions, is responsible for generating proofs for batches of transactions. The proof of a batch (e.g., proving the state transition from ledger hash A to D after multiple transactions) is sent to the L1 Mina blockchain. The state of the Zeko zkApp (the "outer" account on L1) is updated to reflect the new L2 ledger hash only after the batch proof is verified on Mina L1. This anchors the security of the L2 state transitions to the security of the L1 chain.
- **Sequencer Verification:** Even though transactions processed by the sequencer include proofs generated by clients, the sequencer still performs verification. This includes checking that preconditions, permissions, and correct authorisations are met before applying a transaction to the ledger. The sequencer must also prove that it has correctly applied the transaction and verified these additional aspects.
- **Reliance on L1 Consensus:** The Zeko Layer 2 node relies on the Layer 1 Mina consensus for finality. If the L1 experiences rollbacks, the L2 also rolls back to maintain consistency and bridge security.
- **Data Availability:** A critical component for rollups, Zeko's data availability (DA) layer is responsible for storing transaction data. Data availability is ensured by requiring a public key to sign the hashes used, which attests that the necessary data has been shared. The DA layer involves multiple nodes replicating storage.

## Trust Assumptions

The described security model does involve trust assumptions.

- These assumptions include **trust in an honest client**, **honest parties participating in L1/L2 bridging processes**, and **trust in the data availability validator publishing historical data**.
- The MVP version of the Zeko zkApp initially lacked explicit data availability checks for witnesses needed to operate on the zkApp. However, later descriptions of the DA layer indicate mechanisms involving signed hashes and replicated storage to ensure data is available.
- The Zeko L2 node relies on and **trusts the consensus mechanism of the L1 Mina Protocol** for the ultimate finality and integrity of the chain history.

### Developer and User Security Considerations

While Zeko leverages the security of Mina and zero-knowledge proofs, developers and users also have responsibilities regarding security.

- **Smart Contract Permissions and Logic:** Permissions are fundamental in zkApp development for controlling who can interact with and modify a smart contract's state. Different authorisations like `Proof`, `Signature`, and `None` are used. For zkApps, the `Proof` permission is crucial as it requires executing a contract method (`@method`) to authorise state changes, balance transfers, or adding actions.
- **In-Method Security:** Setting permissions to require a `proof` ensures that interactions go through the contract's defined methods. However, the **actual security depends on the logic implemented within those methods**. Developers must include checks and conditions within their `@method`s to restrict who can perform certain actions and under what circumstances (e.g., preventing anyone from draining funds via a `withdraw()` method). Token manager contracts, for instance, require `proof` authorisation for the `access` permission, necessitating token interactions to be approved by calling specific token manager methods.
- **Reducer API Limitation:** Currently, the reducer API in o1js is explicitly noted as **not safe for production applications**. This is due to a limitation where the `reduce()` method breaks if too many actions are pending. Work is ongoing to mitigate this limitation. Developers should be aware of this when using actions and the reducer. Security vulnerabilities can arise when creating updates to unknown accounts within a reducer function.
- **Data Availability and Transaction Status:** Developers should strive to provide users with clear information and a user-friendly interface regarding data posting to the DA layer and the status of their transactions.
